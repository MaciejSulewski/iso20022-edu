## Task 1: data format, content files, check-content rules

**Files:** `src/lib/content-schemas.ts`, `src/lib/content-schemas.test.ts`, `src/content.config.ts`, `src/content/glossary/*.yaml` (new, 18), `scripts/check-content.ts`, `scripts/check-content.test.ts`.

1. `GlossarySchema` (strict) in `src/lib/content-schemas.ts`: `id` (string min 1), `term` (min 1), `plain` (min 1), `message` (string), `elements` (array of string, min 1), `related` (array of string, default `[]`), `lesson` (string, optional), `lastReviewed` (the existing `Reviewed`). A `glossary` collection in `src/content.config.ts` (the existing `yaml()` loader, `src/content/glossary`). Schema tests like the neighbouring ones (accepts a valid term; rejects an unknown key, empty `elements`).
2. check-content rules, in the same style as flows and mappings (add `glossary?: File[]` to `Input`, load it in the CLI, print `Glossary: N`): file parses against the schema; `id` matches the file name; `message` has a schema (the existing messages check); every path in `elements` resolves in the schema; every `related` id exists, is not the term itself, appears once; `lesson` exists when given; no two terms share a `term` (case-insensitive) and no two terms share an element path. Tests for each rule in `scripts/check-content.test.ts`; a deliberately broken term fails each. Show each new rule failing once on real data, then restored (record the break and the error text in your report).
3. Eighteen term files, `src/content/glossary/<id>.yaml`, ids kebab-case of the term. Terms and the element paths to start from (verify each path in the schema; if one does not resolve, pick the right one and say so in your report): debtor (`CdtTrfTxInf/Dbtr`), creditor (`CdtTrfTxInf/Cdtr`), debtor agent (`CdtTrfTxInf/DbtrAgt`), creditor agent (`CdtTrfTxInf/CdtrAgt`), instructing agent (`GrpHdr/InstgAgt`), instructed agent (`GrpHdr/InstdAgt`), intermediary agent (`CdtTrfTxInf/IntrmyAgt1`), message identification (`GrpHdr/MsgId`), end-to-end identification (`CdtTrfTxInf/PmtId/EndToEndId`), instruction identification (`CdtTrfTxInf/PmtId/InstrId`), UETR (`CdtTrfTxInf/PmtId/UETR`), settlement method (`GrpHdr/SttlmInf/SttlmMtd`), interbank settlement amount (`CdtTrfTxInf/IntrBkSttlmAmt`), interbank settlement date (`CdtTrfTxInf/IntrBkSttlmDt`), charge bearer (`CdtTrfTxInf/ChrgBr`), remittance information (`CdtTrfTxInf/RmtInf`), group header (`GrpHdr`), credit transfer transaction information (`CdtTrfTxInf`). One element per term unless a second path is the same thing (no path may be claimed by two terms). `message: pacs.008.001.14`, `lastReviewed: {date: "2026-11-23", by: "unreviewed (AI-drafted, pending T-093)"}`. `lesson`: the lesson that discusses the term, if one does (`what-is-pacs008`, `read-the-xml`, `explore-the-tree`, `follow-the-flow`, `from-mt103`; read the lessons to pick, leave it out when none does). `related`: 1 to 3 other terms that a reader would meet next (for example debtor and debtor agent, end-to-end identification and UETR); every link in both directions is not required.
   - `plain`: one to three sentences in plain words, own wording, a reader new to payments should follow it. Do not state anything the element's schema definition or the lessons do not support (read `src/data/schema/pacs.008.001.14.json` for the definition and the lessons you cite). When unsure, say less.

## Task 2: pages, ElementPanel link, UI text

**Files:** `src/pages/glossary/index.astro` and `src/pages/glossary/[id].astro` (new), `src/pages/lessons/index.astro`, `src/pages/messages/[id]/[...sample].astro`, `src/components/Workspace.tsx`, `src/components/ElementPanel.tsx`, `src/i18n/ui.en.json`, a unit test for the path-to-term map if you add a helper in `src/lib/` (put the helper there, pure, with a test).

1. Pure helper (suggested `src/lib/glossary.ts`): from a list of `{id, term, message, elements}` build `Record<path, {id, term}>` for one message, and sort terms by `term` (case-insensitive). Test: two terms, a path lookup, an element with no term, sorting.
2. `/glossary/` (`index.astro`): `Base` page, title and lead from `t()`, the draft notice (same style and `border-l-accent` box as the mapping page; text through `t()`, e.g. "AI-drafted from the pacs.008.001.14 definitions, not yet reviewed by a person (T-093). Do not rely on it for real payments."), then an alphabetical list: term as link, the plain wording underneath. `data-glossary-list` on the list and `data-glossary-term` on each item, for the browser check.
3. `/glossary/<id>/` (`[id].astro`, `getStaticPaths` over the collection, same style as `mappings/[id].astro`): draft notice, `h1` term, plain wording, section "Official definition" with a short note that it is the ISO text from the schema, then for each element: its ISO name, the path as a link to `${base}messages/${message}/#${path}`, the definition. Read the definition from the schema JSON with `import.meta.glob` and `resolvePath` as the message page does. If an element has no definition, throw at build time. Then "Related terms" (links), the lesson link if any (same wording pattern as the mapping page's), and a link back to the glossary. Static, no island.
4. Lessons index: one link line to the glossary under the list (text through `t()`).
5. Message page: build `path -> {term, href}` from the glossary collection for this message and pass it as a prop `glossary` to `Workspace`, which passes it to `ElementPanel`. In `ElementPanel`, add a section (heading text from `labels`, a new `glossary` label in `PanelLabels` and in the message page's `panel` labels) shown only when the selected node's `path` has a term: a link to the term page. Keep it small; no new fetches.
6. Size: no new client JS beyond the section (check `npm run check:size`; report the workspace page's gzip size before and after).
7. `ui.en.json` keys for everything new. No hard-coded English in templates.
